What Estuary Is

Estuary is a centralized internal finance operations hub for the Arus group of companies. It manages the full money-out lifecycle: someone requests a payment, the right people approve it, finance pays it, the recipient signs for it, and the transaction lands in the accounting system — all in one place, all traceable.

Today that lifecycle is scattered across Google Forms (submissions), Google Sheets with Apps Script (payment vouchers), a petty cash spreadsheet, Kakitangan (expense claims), and SQL Account (books). No system owns the whole picture. The gaps are bridged by humans re-typing data, chasing signatures, and reconciling stale copies of the same record — high-error, unauditable, and unscalable. Signed vouchers go uncollected for months. Apps Script fails silently. Every payment needs at least two people touching it in different systems.

Single source of truth

Every money-out event lives in one system with an immutable audit trail of every state change.

Automated chasing

Signed PV collection happens via one-time tokenised email links and automatic reminders — no human follow-up.

API-first

Every action is a REST endpoint under /api/v1/. The web UI is just one consumer.

AI-operable

An MCP server wraps the API so AI agents can operate finance workflows as callable tools.

Multi-entity from day one

Organization is the top-level partition; one login, an org switcher, per-org roles.

Accounting-aligned

Four transaction dimensions (Agent, Area, GL Code, Project) mirror SQL Account, exported as import-ready CSV.

The Six Payment Types

Payment VoucherDirector (1 step)The MVP priority — replaces the Sheets/Apps Script system
Invoice PaymentNone — direct to paymentLater block
Cash AdvanceManager → Director (2 steps)3-checkpoint reconciliation (2w/3w/4w); overspend links a child advance; unreconciled advances block new ones
Travel AllowanceManager → Director (2 steps)
Expense ClaimNone — direct to paymentStays in Kakitangan until mid-2027
Petty Cash Top-upManager → Director (2 steps)Model pending confirmation (OQ-PettyCashConfirm)

Approval is decided per payment type, not by amount tiers. Internal approvers act only through SSO-authenticated sessions — email is notification, never authorization. External recipients (teachers, contractors, vendors) sign vouchers through one-use, expiring, hashed token links with no login at all.

The workflow engine is data-driven: each submission carries a type-prefixed state (PV_DRAFT) plus a reporting group, and every transition writes an immutable SubmissionTransition row. Workflow definitions, states, and transition rules live in the database — approval chains, email wording, and even theme direction are treated as configuration, not code, so changing policy never means changing code paths.

Where It Stands & What's Next

The design is complete and the workflows are proven — but on a stand-in backbone (local JSON instead of Postgres, dummy sign-in instead of sessions, a file outbox instead of SES). The build direction is single-minded: replace the stand-in backbone with the real one without losing the working flows.
